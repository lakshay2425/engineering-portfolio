Featured · 01InternWare

Backend · Payments · Reliability

₹1 payment vulnerability, and the payment architecture that followed.

Problem

A senior received a Cashfree email confirming a ₹1 payment for a live event registration. Tracing the flow showed that our backend trusted client-provided input when calculating the payment amount, so someone could start a transaction for less than the registration fee.

Decision

Calculate the amount on the backend from trusted registration and pricing data. That closed the hole, but it exposed a second problem: users who had paid were not getting registered. Registration depended on the browser calling our API after payment, and some users closed the tab immediately after paying.

Implementation

Added Cashfree server-to-server webhooks and verified their signatures, because the endpoint is publicly reachable and has to prove that a notification came from the gateway. Added a reconciliation job that periodically checks pending payment records against the gateway and corrects discrepancies.

Outcome

Payment confirmation no longer depends on the browser staying open. When a record differs from the gateway, the gateway’s status is treated as the source of truth. The four architecture versions are shown in the Architecture section.

Featured · 02Resource Hub

Product thinking · UX · Iteration

Five required fields became two.

Problem

Creating a resource required five fields, and every one was mandatory: name, URL, description, tags and visibility. The form added friction before a user had even saved anything. Even though I had built the platform, I wasn’t using it consistently myself.

Decision

Split creation into two phases. Capture asks only for a name and a URL, so a resource can be saved immediately. Organize holds the description, tags, other metadata and visibility, and can happen later.

Implementation

Reworked the creation flow so the first step is the minimum needed to keep a resource, and the remaining fields move into a later organize step.

Outcome

The required inputs dropped from five to two. Saving became one quick action, and organizing became something a user can do later. I haven’t measured adoption, so this story is about the friction removed, not a percentage.

Moving from Firebase to direct Google OAuth.

05Resource Hub

Full-stack · Storage · Async processing

Direct-to-storage document upload with confirmation.

The Express backend issues a pre-signed URL, and the React frontend uploads straight to MinIO, so files never pass through the application server. MinIO then calls a webhook, the backend confirms the upload, updates the database, and hands follow-up work to PG Boss. An uploaded object and a persisted record are two separate things, so the workflow confirms both before a document counts as available.

06InternWare

Authentication · JWT · Cookies

Keeping users signed in across refreshes.

Login worked, but refreshing the page logged users out. I studied JWTs, cookie attributes and how they behave across scenarios, then moved the session to JWT-based authentication with secure HTTP cookies. This was an improvement to an existing authentication flow designed by a senior developer, not an architecture I designed from scratch.

03 — Architecture gallery.

The payment flow in four versions, in order. Each version changed who is trusted to calculate an amount and who is trusted to confirm a payment. Select any diagram to view it at full size.

  1. Architecture 1 · Client-dependent confirmation

    The client calculated the amount, asked the gateway for order details, and told the server when payment succeeded. The backend trusted that input.

  2. Architecture 2 · Server-side amount calculation

    What changed: the server calculates the amount and fetches order details from the gateway. The client still reports success, so confirmation still depends on the browser.

  3. Architecture 3 · Webhook confirmation

    What changed: the gateway confirms payment directly to the server through a webhook. The server verifies the signature before updating the database.

  4. Architecture 4 · Webhook plus reconciliation

    What changed: a cron-driven reconciliation job finds pending records and checks them with the gateway. If the status differs, the gateway wins and the database is updated.

05 — AI-assisted development

AI speeds up implementation. Judgment stays mine.

Cursor implemented public collections, and its PR reviewer raised a valid concern: private resources could be exposed through a public collection. I agreed and asked for the fix. The recommendation was reasonable from a general security standpoint, but it contradicted the product. Adding a private resource to a public collection was an explicit decision to share that resource through that collection.

I caught the problem by testing the real flow. I created a collection with social links and opened its public URL in a browser where I wasn’t logged in. The resources were inaccessible, so the implementation no longer matched what I had designed. I asked Cursor to revert the change.

The sharing model I designed is collection-level sharing, and private resources were never supposed to become globally public. The point of the story isn’t that the AI was careless. A technically sound recommendation can still be wrong for a specific product requirement, and checking that is the engineer’s job.

  • Understand the intended behavior before accepting a fix.
  • Evaluate recommendations against product requirements.
  • Test the actual user flow, not only the diff.
  • Keep responsibility for the final implementation.
